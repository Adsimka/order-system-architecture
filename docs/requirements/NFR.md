# НФТ: Система оформления и обработки заказов

### Нагрузка и продуктовые ожидания:
 - DAU: 2 000 000
 - Действий "оформить заказ" на пользователя в сутки: 0.2
 - Окно пика: 20% суток (≈ 4.8 часа), в это время приходится 80% действий
 - Средний размер ответа на создание заказа: 2 KB
 - Цель UX: "создание заказа ощущается быстрым"
 - Инциденты недопустимы в часы пик (бизнес-ущерб высокий)

### Ограничения:
 - команда 6–8 человек, продукт еще растет
 - бюджет ограничен → "лишняя сложность" нежелательна
 - внешний платежный провайдер (HTTP) может деградировать

### 1. Доступность
Бизнес всегда хочет, чтобы система работала 24/7,   
однако с существующими ограничениями (команда, бюджет и накладные проблемы с внешней системой)  
я предпочитаю **availability = 99,9%** 

**Отразим простой в таблице**:  
Простой в неделю = 24 * 60 * 7 * 0,001 = 10,08 мин  
Простой в месяц = 24 * 60 * 30 * 0,001 = 43,2 мин    
Простой в год = 24 * 60 * 365 * 0,001 = 525,6 / 60 = 8,76 ч   

| **Доступность** | **Простой в год** | **Простой в месяц** | **Простой в неделю** | 
|-----------------|-------------------|---------------------|----------------------|
| 99,9%           | 8,76 ч        | 43,2 мин         | 10,08 мин        |

### Down:

**1.1 Допустимая доля ошибок системы составляет:**    
100% - **availability**(99,9%) = 0,1%  

Ошибочный результат обработки валидного запроса считается неуспешным событием.   
Если доля таких событий превышает 0,1% за установленный период  

**1.2 Расчет пикового Time-based с учетом пикового окна 4.8 ч**

Расчет проведем на 1 месяц:  
**Time-based** = 30 * 4,8 * 60 * 0,001 = 8,64 мин

В пиковые часы система суммарно за месяц не может быть недоступной дольше 8,64 минут

**1.3 Инциденты недопустимы в часы пик**

Существующее условие "Инциденты недопустимы в часы пик" будет рассматриваться в след. ключе:  
Так как система технически не может гарантировать 100% бесперебойную работу, то в часы пика должен присутствовать   
полный запрет на плановые релизы и выкатки миграции

**1.4 Недоступность системы** 

Система будет считать недоступной:  
 - Нарушение способности принимать, валидировать и сохранять заказ 
 - Успешный HTTP-статус, который не сохранил заявку в системе обработки 

### 2. Latency SLO для API (p95/p99) 
Задержка будет считаться от получения запроса edge до отправки последнего байта ответа:
 - p95 <= 300 мс
 - p99 <= 800 мс (допустимый хвост)

### Histogram и PromQL
Сперва напишем общий запрос, который выдаст общую информацию по всем сервисам: 

```
histogram_quantile(
    0.95,
    sum(rate(http_server_requests_seconds_bucket[5m])) by (le)
)
```

Но как правило для анализа реальной системы такой запрос скромен,   
запрос должен быть точнее (например, конкретный под, сервис, успешный/неуспешный запрос и т.д) 
```
histogram_quantile(
  0.95,
  sum (
    rate(orders_edge_request_duration_seconds_bucket{
      service="orders", env="prod", cluster="orders-prod",
      route="/orders", method="POST", outcome="success"
    }[5m])
  ) by (le)
)
```

Здесь указано следующее, что 
 - по service="orders" - мы фильтруем по конкретному сервиву,   
 - по env="prod" - мы фильтруем по конкретному окружению,
 - cluster="orders-prod" - мы фильтруем по конкретному кластеру
 - route="/orders" - мы фильтруем по конкретному URL
 - method="POST" - мы фильтруем по конкретному методу HTTP
 - outcome="success" - мы фильтруем только успешные запросы

Однако, не забываем, что, например, несколько кластеров нельзя смешивать,   
поэтому смотрим их **ВСЕГДА** отдельно

Чтобы посмотреть перцентли для p99, нам достаточно заменить 0.95 на 0.99,   
для пиков добавить period="peak"


### 3. Reliability/Incidents (частота отказов / MTBF как ориентир)

Система не должна допускать более одного критического сбоя за 30 дней.  
В часы пика количество критических сбоев должна быть равно 0

### Критическим сбоем считаем:
 - полную недоступность создания заказов
 - потеря заказа, которую система подтвердила пользователю
 - множественное списание за одну платёжную операцию

Ориентир **MTBF** около **720** часов работоспособности между отказами

### 4. Maintainability (MTTR целевой + практики снижения)

Восстановление системы должно быть равной:
 - не более 5 минут для автоматического восстановления
 - не более 30 минут для ручного восстановления

Целевой простой в 30 дней без учета часов пика составляет 43,2 минуты, соответственно MTTR <= 43,2 минуты

Для поддержания или снижения сопровождаемости необходимо включить след. пункты:  
 - фичефлаги, canary/blue-green, миграции, тесты на откат
 - логирование, трейсы, метрики, профилирование
 - документация процедур и автоматизация рутинных операции

### 5. Scalability (цель по росту нагрузки + как масштабироваться

Расчет общего количества заказов:  
2000000 * 0,2 = **400000** заказов в сутки

Расчет нагрзуки в окно пика:  
400000 * 0,8 = **320000** заказов 

Расчет среднего RPS в окно пика:
4,8 часов = 4,8 * 60 * 60 = 17280 секунд

320000 / 17280 = 18,5 RPS

С учетом того, что в окно пика нагрузка может распределяться неравномерно, будем закладывать x3 от существующей нагрузки: 
Пиковый RPS = 18,5 * 3 = 55,5 RPS

### Масштабирование:

Stateless API масштабируем горизонтально, БД сначала оптимизируем и scale-up.

### 6. Целостность

0 потерь подтвержденных заказов (acknowledged orders) и 0 двойных списаний 

### 7. Безопасность

Все взаимодействия через систему orders проверяют владельца/роль

### 8. Resilience / отказоустойчивость

Система должна быть изолирована от сбоев и деградации внешнего платежного провайдера:  
 - изоляция сбоев, т.е. если произошел всплеск сбоев внешнего шлюза, то система должна прекратить запросы к нему
 - использование Idempotency Key (PostgreSQL / Redis)
 - процесс создания платежа и оплаты должны быть раздельны, чтобы не блокировать друг друга
 - введем Dead Letter Queue для ручного разбора заказов с системными ошибками


# Расчеты BOTEC (на салфетке)

### Расчет RPS:

**RPS_peak** = **55,5** RPS  
**RPS_peak_avg** = **18,5** RPS  
**RPS_avg** = 400000 / 24 / 60 / 60 = **4,63** RPS  

### Конкурентность:

Для p95 нельзя оценить среднее, т.к, редкий хвост может изменить результат.  
Среднее **AvgLatency** примем равной 0,1 с (100 мс)  

**conc_peak** = 55,5 * 0,1 = 5,55 одновременных запросов
**conc_peak_avg** = 18,5 * 0,1 = 1,85 одновременных запросов
**conc_avg** = 4,63 * 0,1 = 0,46 одновременных запросов

### Трафик ingress/egress

**egress/ingress** = 18,5 * 2000 * 8 / 1000000000 = 0,296 Mbps ~ 37 KB/s  

Размер всех ответов за 30 дней:  
400000 * 2 KB * 30 ~ 24 GB

# Хранение данных:
400000 * 30 = **12 млн** заказов в месяц
12 млн * 12 = **144 млн** заказов в год (288 GB)

Увеличим на х2 для на индексы, служебные даные и т.д, тогда получим:   
288 GB * 2 ~ **576 GB в год**

Надо учесть дополнительные резервы для сбоев (накопление очереди):  
18,5 RPS * 2 KB * 30 min (1800 sec) = 66,6 MB    
_или_  
55,5 RPS * 2 KB * 30 min (1800 sec) = 199,8 MB
