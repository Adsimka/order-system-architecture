# ADR-0003: PostgreSQL как единое хранилище идемпотентности (без Redis)

- Status: Proposed
- Date: 2026-10-30
- Owners: Backend Team

## Context
Необходима идемпотентность для двух потоков: 
 - создание заказа (защита от повторных POST от клиента) 
 - обработка webhook (защита от повторной доставки от провайдера). 


## Decision
Использовать только PostgreSQL с таблицей idempotency_keys.   
Ключи записываются в рамках той же локальной транзакции, что и бизнес-операция (создание заказа или обновление платежа).   
Проверка идемпотентности через уникальный индекс или SELECT ... FOR UPDATE перед бизнес-логикой.

## Alternatives considered
1) Redis как основное хранилище - быстрее на чтение, но требует синхронизации с PostgreSQL и рискует рассинхронизацией при сбое Redis; усложняет rollback и восстановление
2) Комбинация Redis + PostgreSQL (кэш + персистентность) - быстрее, но добавляет вторую точку отказа, усложняет консистентность и эксплуатацию для команды 6-8 человек
3) In-memory локальный кэш - теряется при рестарте пода, не работает при горизонтальном масштабировании API

## Consequences
- Единый источник истины: нет рассинхронизации между кэшем и БД, проще диагностировать и откатывать
- Атомарность: идемпотентность гарантируется в рамках той же транзакции, что и бизнес-операция
- Меньше инфраструктуры: не нужно разворачивать, мониторить и бэкапить Redis
- Приемлемая производительность: при пиковых 55.5 RPS нагрузка на таблицу idempotency_keys незначительна, простой индекс покрывает запросы
- При росте нагрузки в 10x+ можно добавить Redis как кэш чтения без изменения бизнес-логики
