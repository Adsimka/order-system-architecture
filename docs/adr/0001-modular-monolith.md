# ADR-0001: Модульный монолит для обработки и оформления заказов

- Status: Proposed
- Date: 2026-10-29
- Owners: Backend Team

## Context
После создания заказа необходимо инициировать оплату.  
Нельзя потерять заказ при сбоях или ошибках, а медленный провайдер не должен растягивать POST.   
Одной локальной транзакцией нельзя атомарно записать PostgreSQL и произвольный внешний HTTP-эффект.

## Decision
Сохранять заказ и idempotency сущность в одной PostgreSQL-транзакции со статусом PENDING_PAYMENT.  
Async Worker периодически опрашивает таблицу платежей на наличие зависших статусов и выполняет идемпотентный запрос статуса к провайдеру с durable retry.  
Retry-логика и Dead Letter Queue реализуются через служебные колонки в бизнес-таблице.
Семантика доставки at-least-once, стабильные event_id/payment_attempt_id, идемпотентность на стороне получателя.

## Alternatives considered
1) Микросервисы - независимый deploy/scale и изолированные данные, но сетевые отказы, трассировка, согласованность и эксплуатация слишком дороги для текущей нагрузки
2) Один процесс для HTTP и всех фоновых задач - проще deploy, но медленная оплата может исчерпать общие ресурсы и потребовать масштабировать всё сразу
3) Монолит без модульных границ - быстрее в реализации, но изменения распространяются между модулями и усложняют сопровождение

## Consequences
Меньше инфраструктуры, локальные транзакции и проще диагностировать и откатывать.
- API и worker масштабируются раздельно
- бизнес-модули пока имеют общий release и DB.   
Проверяем зависимости модулей и запрещаем прямой доступ к чужим внутренним таблицам из прикладного кода
Микросервис выделяем при подтверждённой потребности в независимых релизах, отдельном владельце или существенно отличающемся профиле нагрузки, а не при достижении произвольного RPS.
